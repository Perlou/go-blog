# 博客文章写作模板

> 给 AI 协作者用的写作模板。基于 14 篇已发布文章观察到的真实模式。
> 想要可被自动加载的 skill 形态见 [`skills/blog-writing/SKILL.md`](../skills/blog-writing/SKILL.md)。

---

## 一、快速模板（你贴这个给 AI 就行）

```
帮我写一篇博客文章：

【主题】：<一句话概括>
【类型】：<深度解析 | 手册 | 全面攻略 | 项目分享 | 经验总结 | 随笔>
【要点】：
- <要点 1>
- <要点 2>
- <要点 3>

【可选】：
- 长度：<简短 800-1500 / 中等 1500-3000 / 详细 3000-8000 / 长文 8000+>
- 面向读者：<初学 / 中级 / 高级 / 通用>
- 包含代码：<是 / 否>
- 已有材料：<相关链接 / 笔记 / 之前的 PR / GitHub repo>
- 特殊要求：<...>

封面图：自动从 manifest 随机抽一张
（也可以单独说"用 xxx-yyy 这张"或"生成 zzz 主题的"）
```

## 二、Front Matter 标准

```toml
+++
date = '2026-05-01T11:00:00+08:00'
draft = false
title = '文章标题'
image = '/images/bg/<cover>.webp'
categories = ['<分类>', ...]
tags = ['<标签>', ...]
+++
```

| 字段 | 规则 |
|---|---|
| `date` | ISO 8601 + `+08:00`（北京时间）；与文件名日期一致 |
| `draft` | 写作中 `true`；发布前改 `false` |
| `title` | 中文 + 必要英文；< 25 字优先；按下面"标题模式"四选一 |
| `image` | 必填；`/images/bg/<file>.webp`；**文件必须真实存在**（否则 build 失败） |
| `categories` | 1-2 个；**只能从下方"真实分类池"选**，不要造新分类 |
| `tags` | 3-5 个；从下方"真实标签池"选；前 2 个最具体 |

### 真实分类池（按实际频率）

```
['AI', '技术']        ← 最常用，AI / Agents / RAG / LLM / Claude Code / Harness
['Python', '技术']    ← Python 库 / 数据 / 深度学习
['技术']              ← 通用工具 / 项目分享，非 AI 非 Python
['随笔', '投资']      ← 行业观察 / 个人思考（罕用）
```

**禁止**生造：`技术分享` / `AI开发` / `项目实践` / `工具推荐` / `读书笔记`
等没用过的分类。

### 真实标签池（按使用频率）

| 类别 | 标签 |
|---|---|
| AI 必备 | `AI` · `Agents` · `RAG` · `LLM` · `大模型` · `深度学习` |
| AI 主题 | `LangChain` · `LlamaIndex` · `RAGAS` · `Hugging Face` · `Claude Code` · `Harness` · `OpenClaw` |
| Python | `Python` · `NumPy` · `Pandas` · `PyTorch` · `数据分析` |
| 项目 / 工具 | `开源项目` · `开发工具` · `效率` · `API测试` · `Cloudflare` · `React` · `TypeScript` |
| 随笔类 | `XR` · `Vision Pro` · `Meta Ray-Ban` · `空间计算` · `投资` |

**约定**：AI 类必带 `AI`，几乎必带 `Agents`；大小写遵守池里写法。

## 三、五种结构模板（按文章类型选）

### A. 深度解析 / 完整指南（最常用，~50%）

适用：把一个新概念 / 框架 / 范式从零讲透。例：`LangChain`、`Ragas`、
`LlamaIndex`、`Harness Engineering`。

**标题模式**：

- "X 深入解析：从零开始的完整指南"
- "深入解析 X"
- "X：副标题（点出核心论点）"

**结构骨架**：

```markdown
+++
... front matter ...
+++

# 标题

> （可选）开场金句或链接到配套实现

---

## 目录

- [一、X 是什么？](#一x-是什么)
- [二、为什么需要 X？](#二为什么需要-x)
- ... 共 8-12 节
- [十二、总结与学习路径](#十二总结与学习路径)

---

## 一、X 是什么？

### 1.1 定义
### 1.2 ...

## 二、为什么需要 X？
### 2.1 痛点
### 2.2 X 的解法
### 2.3 ...

## 三、核心概念 / 三条核心理念

## 四、五阶段生命周期 / 主要 API 等

## 五、...

## 十一、参考实现 / 配套代码（如有）
> GitHub 链接、3 行代码安装命令、剧本演示

## 十二、总结与学习路径

### 12.1 核心要点回顾
（ASCII 知识图谱）

### 12.2 推荐学习路径
（按 Week 1 / Week 2 ... 分阶段）

### 12.3 自我检查清单
（10 条 □ 形式）

### 12.4 参考资源
（表格：资源 / 链接 / 用途）

### 12.5 一段话作为结尾
> 金句收尾
```

### B. 手册 / 速查（中等频率，~15%）

适用：把一个工具 / 库的常用 API 整理成查询表。例：`NumPy 手册`、
`Pandas 手册`、`PyTorch 手册`、`Hugging Face 速查手册`。

**标题模式**：

- "X 手册"
- "X 速查手册"

**结构骨架**：

```markdown
## 简介
（一两段说明 X 是什么、本手册覆盖什么）

## 安装

## 基础概念

### 概念 1
### 概念 2

## 常用 API

### 类别 1：xxx
| 方法 | 用途 | 示例 |
|---|---|---|

### 类别 2：xxx
| 方法 | 用途 | 示例 |
|---|---|---|

## 实战示例

### 示例 1：xxx

### 示例 2：xxx

## 常见问题

## 参考资源
```

### C. 全面攻略 / 实战（中等频率，~15%）

适用：把一个工具 / 平台从安装到精通的全流程整理。例：`Claude Code 全面攻略`、
`OpenClaw 云服务器部署方案`、`常用 RAG 方案解析`。

**标题模式**：

- "X 全面攻略"
- "X 实战"
- "X 部署方案"
- "常用 X 方案解析"

**结构骨架**：

```markdown
## 背景：X 是什么、解决什么问题

## 核心概念

## 安装与配置

## 实战路径

### 场景 1：xxx
### 场景 2：xxx

## 进阶技巧

## 最佳实践

## 常见坑 / 注意事项

## 总结
```

### D. 项目分享（中等频率，~10%）

适用：发布或回顾一个自己做的开源项目。例：`基于 Google Antigravity 开发 Httping`。

**标题模式**：

- "基于 X 开发 Y：副标题"
- "我做了一个 X：副标题"

**结构骨架**：

```markdown
## 项目初衷
（为什么做这个；想解决的痛点）

## 技术选型
（技术栈 + 理由对照表）

## 核心功能展示
（截图 / GIF / 关键代码）

## 开发历程

### 阶段 1：xxx
### 阶段 2：xxx

## 开发感受 / 反思
（哪里栽过坑 / 学到什么）

## 未来规划

## 总结

🔗 GitHub: [...]
⭐ Star 一下吧～
```

### E. 经验 / 随笔（低频，~10%）

适用：行业观察 / 个人思考 / 学习总结。例：`关于 XR 行业和 AI 智能眼镜的一些观察`。

**标题模式**：

- "关于 X 的一些观察"
- "X：原理、架构与实战思考"
- "X 的一些思考"

**结构骨架（随笔可不要章节标题）**：

```markdown
（开篇 2-3 段营造氛围）

## 背景 / 现象

## 观察 1：xxx

## 观察 2：xxx

## 观察 3：xxx

## 反思 / 展望

## 一段话作为结尾
> 金句
```

## 四、写作风格红线

### ✅ 应该做的

- **中文优先**，专有名词保留英文（`LLM` / `RAG` / `Hugo` / `Zod`）
- **二级标题分章** (`##`)，三级展开 (`###`)
- **代码块带语言标识**：` ```python ` / ` ```typescript ` / ` ```bash `
- **代码块要有注释**，关键变量名要表意
- **emoji 适度点缀**：🚀 ⚡ 🎨 💡 ✨ 📦 🎯 🛡️
- **结尾呼应开头** + 给 takeaway
- **中英文之间加空格**："使用 React 开发"
- **数字与单位之间加空格**："5 个用例" / "3000 字"
- **代码示例完整可运行**（或显式标 "伪代码"）

### ❌ 避免做的

- ❌ 标题过长 / 标题党
- ❌ 大段文字没分段（一段超 5 行就该断）
- ❌ 代码块没有语言标识（裸 ` ``` `）
- ❌ 通篇没有代码 / 例子（除随笔外）
- ❌ 章节失衡（有的 1 行有的 50 行）
- ❌ 滥用 emoji（每段都来一个 = 没意义）
- ❌ 中英混排不空格
- ❌ 给主题不消费的 front matter 字段（`description` / `summary` 等）
- ❌ 直接 `<img>` 远端 URL（用本地 `/images/...` 路径走 srcset）

## 五、封面图（必填）

每篇文章必须有 `image` 字段。三个来源（按推荐顺序）：

### 1. AI 生成（最方便，推荐）

```bash
# 一次性配置
brew install webp jq
cp .env.example .env             # 填入 GEMINI_API_KEY

# 随机一张
./scripts/generate-bg-batch.sh -n 1

# 多张备选
./scripts/generate-bg-batch.sh -n 5

# 指定主题
./scripts/generate-bg.sh tibet-yamdrok "Yamdrok sacred lake at sunrise..."
```

详见 [`scripts/README.md`](../scripts/README.md)。manifest 共 65 条，覆盖
38 个国家 / 地区。

### 2. 复用现有

`assets/images/bg/` 下挑一张主题相符的：

```bash
ls assets/images/bg/
```

### 3. 自带图片

```bash
cwebp -q 80 input.jpg -o assets/images/bg/<name>.webp
```

文件命名：kebab-case 英文，`<region>-<landmark>.webp`（自然风光）或
`<topic>.webp`（技术主题）。

## 六、文件命名

```
content/post/YYYY-MM-DD-url-friendly-title.md
```

- 日期使用文章创建当天
- title 用英文 / 拼音的小写 url-safe 形式（**不要纯中文文件名**）
- 不要省略日期前缀

例：

```
content/post/2025-11-21-react-19-features.md
content/post/2026-03-05-ragas.md
content/post/2026-05-01-harness-engineering.md
```

## 七、四个真实示例（按四种类型）

### 示例 1：深度解析

```
帮我写一篇博客文章：

【主题】：详细解析 LangGraph，多 agent 编排框架
【类型】：深度解析
【要点】：
- LangGraph 的核心抽象（StateGraph / Node / Edge）
- 与 LangChain Agent 的关系与差异
- 三种典型工作流（顺序 / 分支 / 循环）
- 与 Human-in-the-loop 的整合
- 实战：构建一个研究员 Agent

【可选】：
- 长度：详细 5000-8000
- 面向读者：中级
- 包含代码：是
- 已有材料：https://langchain-ai.github.io/langgraph/
```

### 示例 2：手册

```
帮我写一篇博客文章：

【主题】：FastAPI 速查手册
【类型】：手册
【要点】：
- 快速安装与最小项目
- 路由 / 路径参数 / 查询参数
- Pydantic 模型与验证
- 依赖注入
- 异步路由
- 文件上传 / 流式响应
- 部署（Uvicorn / Gunicorn / Docker）

【可选】：
- 长度：详细
- 包含代码：是（每个 API 配最小可运行示例）
```

### 示例 3：项目分享

```
帮我写一篇博客文章：

【主题】：用 Claude Code 几小时撸出一个 Markdown 渲染服务
【类型】：项目分享
【要点】：
- 项目背景：为什么不用现成的（自定义渲染需求）
- 技术栈：Hono + remark + Cloudflare Workers
- 核心实现的几个有意思的点
- Claude Code 在这次开发里帮我做了什么
- 部署到 Cloudflare Workers 的过程
- 项目链接 + 求 Star

【可选】：
- 包含代码：是（关键片段）
- 长度：中等 2000-3000
```

### 示例 4：随笔

```
帮我写一篇博客文章：

【主题】：用 Claude Code 三个月之后的一些观察
【类型】：随笔
【要点】：
- 工具不是替代写代码，而是改变写代码的"动作单元"
- 哪些场景 Claude Code 显著加速，哪些反而更慢
- 团队协作时的新分工方式
- 对工程师价值的重新审视

【可选】：
- 长度：中等
- 风格：感性 + 理性
```

## 八、输出 / 提交检查清单

提交前 AI 应当自检：

- [ ] front matter 五个字段齐全（date / draft / title / image / categories / tags）
- [ ] `image` 引用的文件真实存在 (`ls assets/images/bg/<file>.webp`)
- [ ] categories 来自真实池，不造新分类
- [ ] tags 3-5 个，前 2 个最具体
- [ ] 标题 < 25 字，套用四种模式之一
- [ ] 所有代码块都带语言标识
- [ ] 中英文之间有空格
- [ ] 数字与单位之间有空格
- [ ] 所有章节都有内容（没留 TODO 占位）
- [ ] 结尾有总结 / takeaway
- [ ] `hugo server` 本地预览无报错

## 九、补充说明

1. **日期**：使用文章创建当天，格式 `YYYY-MM-DDThh:mm:ss+08:00`
2. **长度**：根据主题复杂度，不要为字数凑
3. **代码质量**：例子必须是最佳实践，关键处加注释
4. **链接引用**：相关资源用 markdown 行内链接
5. **写完别忘**：跑 `./publish.sh` 一键发布

## 一段话精要

技术博客的价值不在"写得多"，而在"让读者真的学到东西"。**结构决定可读性，
代码决定可信度，例子决定可记忆性。** 三者俱全，文章就有生命力。
