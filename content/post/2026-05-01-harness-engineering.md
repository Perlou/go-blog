## 一、Harness Engineering 是什么？

### 1.1 定义

**Harness Engineering**（中译：**驭缰工程**）是 OpenAI 于 2026 年 2 月公开提出的工程范式。一句话定义：

> **工程师不再以"写代码"为主要产出物，而是以"设计环境、明确意图、构建反馈回路"为主要产出物，让 AI 智能体可靠地完成具体工作。**

```
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│        传统范式                       Harness 范式               │
│                                                                │
│   ┌──────────────┐                ┌──────────────┐            │
│   │  工程师亲手   │                │  工程师设计   │            │
│   │  编写业务逻辑 │                │  环境与约束   │            │
│   └──────┬───────┘                └──────┬───────┘            │
│          ▼                               ▼                    │
│   ┌──────────────┐                ┌──────────────┐            │
│   │  代码 = 产出  │                │ Agent 在约束  │            │
│   │              │                │ 内产出代码    │            │
│   └──────────────┘                └──────────────┘            │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

它的核心论点不是"用 AI 替代工程师"，而是**重新定义工程师的高价值产出物**。

### 1.2 "Harness" 这个词的含义

英文 *harness*：**马具、缰绳、束带**。这个词的语义同时包含两层：

```
┌─────────────────────────────────────────────────┐
│                                                 │
│    Harness = 约束 + 驱动                         │
│                                                 │
│    约束（Constrain）:                            │
│      让一头有力但不可控的动物走在道路上            │
│      → 防止 agent 做出危险动作                    │
│                                                 │
│    驱动（Drive）:                                │
│      把这股力量用在该用的地方                      │
│      → 让 agent 的能力被有效利用                   │
│                                                 │
└─────────────────────────────────────────────────┘
```

任何把 harness 仅仅理解为"防御性 wrapper"或"安全围栏"的做法，都丢掉了"驱动"那一半含义。

### 1.3 一段话精要

| 维度 | 内容 |
|---|---|
| **范式提出方** | OpenAI |
| **首次公开时间** | 2026 年 2 月 |
| **核心主张** | 工程师设计环境，让 agent 可靠完成工作 |
| **主要产出物** | 契约、规则、模板、反馈回路、运行工件 |
| **关键名词** | Intent / Plan / Check / Approve / Execute / Trace |
| **关键边界** | agent 内部可以是黑盒，agent 与世界的接口必须是白盒 |

## 二、为什么需要 Harness Engineering？

### 2.1 软件工程范式的代际演进

把过去几十年的工程范式按"工程师每天主要在产出什么"做一次盘点：

| 代际 | 主要产出 | 核心工件 | 关键技术 |
|---|---|---|---|
| **1. 手写时代** | 业务逻辑代码 | 函数、类、模块 | 编程语言、数据结构 |
| **2. 框架时代** | 配置 + 业务代码 | Controller、Schema、配置 | Spring、Rails、Django |
| **3. 平台时代** | 服务装配 + 编排 | Helm chart、IaC、CI/CD | Kubernetes、Terraform |
| **4. AI 辅助时代** | Prompt + 代码 review | Prompt 模板、code review | Copilot、Cursor |
| **5. Harness 时代** | 环境、契约、规则、回路 | Schema、Policy、Trace、Approval | LLM SDK、契约校验 |

每一代的产出都比上一代"更高一层"：

```
                                              ┌──────────────────┐
                                              │ Harness 时代       │
                                              │ 设计 agent 的世界  │
                                              └─────────┬────────┘
                                                        │
                                    ┌──────────────────┐│
                                    │ AI 辅助时代       ││
                                    │ Prompt + Review  ││
                                    └─────────┬────────┘│
                                              │         │
                          ┌──────────────────┐│         │
                          │ 平台时代           ││         │
                          │ 编排服务          ││         │
                          └─────────┬────────┘│         │
                                    │         │         │
              ┌──────────────────┐  │         │         │
              │ 框架时代           │  │         │         │
              │ 配置 + 代码       │  │         │         │
              └─────────┬────────┘  │         │         │
                        │           │         │         │
┌──────────────────┐    │           │         │         │
│ 手写时代           │    │           │         │         │
│ 编写代码          │    │           │         │         │
└─────────┬────────┘    │           │         │         │
          ▼             ▼           ▼         ▼         ▼
   业务逻辑代码    业务+配置     编排定义   提示词     约束规则
```

### 2.2 AI 时代的工程困境

在 LLM 真正进入生产之前，工程师对"系统行为可信"的信心来自三件事：

```
传统系统的可信感来源：
├── 控制流是显式的       → 我能在代码里读出每一步
├── 输入输出是确定的      → 同样输入，同样输出
└── 行为可被静态推理      → review 代码就能发现 bug
```

LLM 进入生产后，**这三件事都瓦解了**：

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│   LLM 引入后的三个崩溃                               │
│                                                     │
│   ❌ 控制流不再显式                                  │
│      模型内部是 transformer 黑盒，没法"读出"         │
│                                                     │
│   ❌ 输出不再确定                                    │
│      同样 prompt 可能产生不同结果                    │
│                                                     │
│   ❌ 静态推理失效                                    │
│      代码 review 看不出"prompt 注入"导致的崩溃       │
│                                                     │
└─────────────────────────────────────────────────────┘
```

工程师的传统手段全部失效。**Harness Engineering 是对这种困境的系统性回应。**

### 2.3 Harness 解决了什么

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│   问题                          Harness 的解法                    │
│   ────────────────────────      ────────────────────────────     │
│                                                                  │
│   控制流不再显式                  显式契约 + 显式规则 + 显式审批门 │
│   ↓                              ↓                               │
│   "agent 内部不可见"               "接口和决策点完全可见"           │
│                                                                  │
│   输出不再确定                    Schema 校验 + 失败可重试         │
│   ↓                              ↓                               │
│   "agent 可能瞎写"                 "瞎写会被拦下，且可以被修复"     │
│                                                                  │
│   静态推理失效                    运行工件 + Trace 时间线         │
│   ↓                              ↓                               │
│   "review 代码看不出 bug"          "review 工件能还原决策过程"     │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

**关键洞察**：Harness 不试图让 agent 变得确定，而是**让 agent 与世界之间的接口变得确定**。

## 三、三条核心理念

Harness Engineering 建立在三条互相支撑的主张上。理解这三条，就理解了 80% 的范式。

### 3.1 理念 A：仓库内工件就是系统的事实来源

#### 3.1.1 传统系统中的"事实分散"问题

在 harness 范式之前，"系统怎么决策"散布在多处：

```
传统系统的事实来源：
├── 代码（控制流）                    ← 工程师能 review
├── 数据库里的 feature flag           ← 工程师不一定能 review
├── 工程师脑子里的隐式规则             ← 没法 review
└── Slack 里某条 thread 的口头共识    ← 完全没法 review
```


#### 3.1.2 Harness 的做法：上移到仓库

把上述所有事实**显式化、文件化、git 可追踪化**：

```
┌────────────────────────── 仓库 ─────────────────────────┐
│                                                         │
│  contracts/                  ← 输入输出契约              │
│    intent.schema.ts                                     │
│    plan.schema.ts                                       │
│                                                         │
│  policies/                   ← 决策规则                  │
│    pii-fields.yaml                                      │
│    require-approval.yaml                                │
│                                                         │
│  scenarios/                  ← 场景检查                  │
│    row-budget.yaml                                      │
│                                                         │
│  prompts/                    ← agent 指令                │
│    planner.tmpl                                         │
│                                                         │
│  runs/                       ← 历史运行依据              │
│    2026-04-15-r3k9/                                     │
│                                                         │
└─────────────────────────────────────────────────────────┘
              │
              ▼
       这些工件可以被：
       - commit
       - review
       - diff
       - rollback
              │
              ▼
   系统行为的演变史 = git history
```

#### 3.1.3 一句话总结

> **"Where do the rules live?" 的答案应当是 "in the repo"。**

### 3.2 理念 B：约束应当被编码为显式、可检查的规则

#### 3.2.1 模糊感 vs 确定感

工程师对 AI 系统的焦虑通常表达为："我不放心让 agent 直接动数据库。"

Harness 的回答不是"再训练得好一点"或"再 prompt 调好一点"，而是：

```
┌───────────────────────────────────────────────────────┐
│                                                       │
│   Agent 内部 = 黑盒（接受不确定）                       │
│                                                       │
│       ┌─────────────────────┐                         │
│       │  ╱╲╱╲╱╲╱╲╱╲╱╲╱╲    │  ← 不可控、概率性          │
│       │  Transformer 内部    │                         │
│       │  ╲╱╲╱╲╱╲╱╲╱╲╱╲╱    │                         │
│       └──────────┬──────────┘                         │
│                  │                                    │
│   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │
│                  │                                    │
│   Agent 与世界的接口 = 白盒（强制确定）                  │
│                                                       │
│       ┌──────────▼──────────┐                         │
│       │   Schema 校验         │                         │
│       │   Policy 校验         │                         │
│       │   Scenario 校验       │                         │
│       │   人工审批门          │                         │
│       └──────────┬──────────┘                         │
│                  │                                    │
│       ┌──────────▼──────────┐                         │
│       │   现实世界（DB / API） │                         │
│       └─────────────────────┘                         │
│                                                       │
└───────────────────────────────────────────────────────┘
```

#### 3.2.2 三种"约束被编码"的具体形态

```
1. 输入输出契约（Schema）
   ├── 用 JSON Schema / Zod / Pydantic 定义
   ├── agent 必须返回符合 schema 的结构化对象
   └── 不合法 → 立即拒绝，不进入下游

2. 决策规则（Policy）
   ├── 用 yaml / json / DSL 定义
   ├── 例如："customers.email 不允许出现在 SELECT 中"
   └── 命中 → 拒绝 / 重试 / 走审批

3. 场景规则（Scenario）
   ├── 状态相关的检查
   ├── 例如："estimated rows > 10000 时拒绝执行"
   └── 是 lint 之上的、运行时感知的检查
```

#### 3.2.3 一段反例代码

下面这段代码**不是 harness 工程**，只是带名字的传统代码：

```typescript
// ❌ 反模式：规则藏在控制流里
function generateSql(intent: string): string {
  const sql = llm.generate(intent)
  if (sql.includes("email")) {        // 隐式规则
    throw new Error("PII")
  }
  if (!sql.includes("WHERE")) {       // 隐式规则
    throw new Error("missing WHERE")
  }
  return sql
}
```

**判别标准**：删掉所有 yaml / schema 文件后，系统行为是否完全不变？如果是，说明规则没有真正被外化。

下面这段才是：

```typescript
// ✅ 正例：规则在 yaml 里，代码只解释规则
function generateSql(intent: string): SqlAction {
  const sql = llm.generate(intent)
  const findings = policyEngine.check(sql, loadPolicies("./policies/"))
  if (findings.some(f => f.level === "error")) {
    return reject(findings)
  }
  return accept(sql)
}
```

`./policies/` 下的 yaml 才是规则的真正所在。

### 3.3 理念 C：工程的真正价值在于搭建脚手架

这是最反直觉、也最重要的一条。

#### 3.3.1 价值移位

```
┌─────────────────── 工程师价值的位移 ──────────────────┐
│                                                       │
│   传统认知                          Harness 认知       │
│   ──────────────                    ──────────────    │
│                                                       │
│   写出能跑的代码                     写出"让 agent 写出  │
│   ↓                                  的代码能可靠跑"    │
│   = 高价值                            的环境            │
│                                      ↓                │
│                                      = 高价值          │
│                                                       │
│   写一个能处理 95%                    设计一份能拦下     │
│   输入的函数                          5% 危险输入       │
│   ↓                                   的 policy        │
│   高价值                              ↓                │
│                                       高价值           │
│                                                       │
└───────────────────────────────────────────────────────┘
```

#### 3.3.2 高价值产出物清单

在 harness 范式下，工程师该把时间花在：

| 产出物 | 它回答什么问题 |
|---|---|
| **契约（Schema）** | "系统该接受 / 拒绝什么样的输入和输出？" |
| **规则（Policy）** | "在什么情况下做什么决定？" |
| **环境（Sandbox）** | "agent 能看到什么、能动什么、不能动什么？" |
| **反馈回路（Feedback）** | "系统如何从每一次运行中学到经验？" |
| **审计工件（Trace）** | "为什么系统在这次运行中做了这个决定？" |

#### 3.3.3 一句话潜台词

> **写代码的工作正在被 agent 接管。为 agent 设计能跑得稳的世界 —— 这件事是当下工程师真正的杠杆。**

## 四、五阶段生命周期

任何一次 agent 工作，在 harness 范式下都被分解为五个明确阶段。这是范式最具操作性的部分。

### 4.1 整体流程

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│                   Harness 五阶段生命周期                          │
│                                                                 │
│   用户原始请求                                                    │
│        │                                                        │
│        ▼                                                        │
│   ┌─────────┐                                                   │
│   │ Intent  │  自然语言 → 结构化意图                              │
│   └────┬────┘                                                   │
│        │                                                        │
│        ▼                                                        │
│   ┌─────────┐                                                   │
│   │  Plan   │  意图 → 结构化执行计划                              │
│   └────┬────┘                                                   │
│        │                                                        │
│        ▼                                                        │
│   ┌─────────┐  ┌──────────┐  ┌──────────┐                       │
│   │  Check  │──│  Schema  │  │  Policy  │  │  Scenario  │       │
│   └────┬────┘  └──────────┘  └──────────┘  └────────────┘       │
│        │                                                        │
│        ▼                                                        │
│   ┌─────────┐                                                   │
│   │ Approve │  低风险自动；高风险等待人工                          │
│   └────┬────┘                                                   │
│        │                                                        │
│        ▼                                                        │
│   ┌─────────┐                                                   │
│   │ Execute │  事务性变更                                         │
│   └────┬────┘                                                   │
│        │                                                        │
│        ▼                                                        │
│   ┌─────────┐                                                   │
│   │  Trace  │  全过程事件流持久化                                  │
│   └─────────┘                                                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 Intent（意图规范化）

#### 4.2.1 输入输出

```
输入：用户的自然语言请求
       例："帮我清理一下过期的优惠券"

输出：结构化 IntentSpec
       {
         goal: "mutate",
         scope: { tables: ["coupons"] },
         timeWindow: { from: "...", to: "..." },
         assumptions: ["过期 = expires_at < now()"],
         riskLevel: "write-low",
         successCriteria: ["所有过期优惠券状态 = inactive"]
       }
```

#### 4.2.2 为什么需要这一步

自然语言里藏着大量被默认的假设：

```
"帮我清理一下过期的优惠券"
            ↓
   解码后藏着的假设：
   ├── "清理" = ? （删除？归档？置无效？）
   ├── "过期" = ? （expires_at 字段？还是别的判断？）
   ├── 是否包括"已使用但过期"的？
   ├── 是否要保留审计记录？
   └── 是否需要发通知？
```

**Intent 阶段强制把这些假设外化，让用户在 plan 之前就能看到"系统怎么理解了我"。**

#### 4.2.3 IntentSpec 的最小字段

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `rawText` | string | ✅ | 用户原文 |
| `goal` | enum | ✅ | query / aggregate / mutate / export |
| `scope` | object | ✅ | 涉及的表 / 资源 |
| `assumptions` | string[] | ✅ | 系统做了哪些隐式假设 |
| `riskLevel` | enum | ✅ | read / write-low / write-high |
| `successCriteria` | string[] | ⚠ | 成功的判断标准 |

### 4.3 Plan（计划生成）

#### 4.3.1 核心约束：Plan 必须是结构化的

```
❌ 错误：plan 是自由文本
"我会先 SELECT 找出过期的，然后 UPDATE 状态..."

✅ 正确：plan 是结构化对象
{
  steps: [
    { kind: "sql", mode: "read", sql: "SELECT id FROM coupons WHERE expires_at < ?" },
    { kind: "sql", mode: "write", sql: "UPDATE coupons SET status='inactive' WHERE id IN (?)" }
  ],
  rationale: "..."
}
```

**为什么必须结构化？** 因为下游 check 阶段需要程序化检查每一步，自由文本无法被静态分析。

#### 4.3.2 Plan 是建议，不是事实

这一点容易被忽视：**Plan 阶段产出的是"agent 想做什么"，不是"已经做了什么"。** 真正的写入要等到 Execute 阶段。

```
┌────────────────────────────────────────────────────┐
│                                                    │
│   Plan = 建议                Execute = 事实          │
│                                                    │
│   ┌──────────┐               ┌──────────┐         │
│   │  agent 说 │              │  系统做   │         │
│   │  "我想 X"  │              │  "做了 X" │         │
│   └──────────┘               └──────────┘         │
│                                                    │
│   只是文本                    数据库已变化           │
│   (尚未发生)                  (已经发生)            │
│                                                    │
└────────────────────────────────────────────────────┘
```

### 4.4 Check（三道并联检查）

#### 4.4.1 三道检查的分工

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│                        Check 阶段                         │
│                                                          │
│           ┌─────────────────┴─────────────────┐         │
│           ▼                ▼                  ▼         │
│   ┌──────────────┐ ┌──────────────┐  ┌──────────────┐   │
│   │ Schema Check │ │ Policy Check │  │ Scenario Eval│   │
│   ├──────────────┤ ├──────────────┤  ├──────────────┤   │
│   │              │ │              │  │              │   │
│   │ 结构是否合法  │ │ 是否违反规则  │  │ 状态下合不合理│   │
│   │              │ │              │  │              │   │
│   │ 例：          │ │ 例：          │  │ 例：          │   │
│   │ JSON 字段     │ │ PII 字段     │  │ 估算行数     │   │
│   │ 全部到位？    │ │ 不该出现     │  │ 是否超限？    │   │
│   │              │ │              │  │              │   │
│   │ SQL 引用的    │ │ 写操作必须   │  │ 跨表 join    │   │
│   │ 列存在？      │ │ 走审批       │  │ 副作用预测    │   │
│   │              │ │              │  │              │   │
│   └──────────────┘ └──────────────┘  └──────────────┘   │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

#### 4.4.2 三道检查的差异

| 维度 | Schema | Policy | Scenario |
|---|---|---|---|
| **关心什么** | 结构合不合法 | 是否违反规则 | 当前状态下合不合理 |
| **依赖什么** | schema 定义 | policy 规则 | 运行时数据 |
| **典型例子** | 缺字段、类型错 | PII、写权限 | 行数、连接深度 |
| **失败动作** | 直接拒绝 | 拒绝 / 审批 | 拒绝 / 警告 |
| **是否有状态** | ❌ 无状态 | ❌ 多数无状态 | ✅ 状态相关 |

#### 4.4.3 失败路径

```
Check 失败
    │
    ├── Schema 失败 ─→ 立即拒绝（结构都不对，下游没法处理）
    │
    ├── Policy 失败 ─→ 三种路径
    │                  ├── reject（直接拒绝）
    │                  ├── retry（修改后重试，反馈给 agent）
    │                  └── escalate（请求审批）
    │
    └── Scenario 失败 ─→ 通常 reject，部分 warning
```

#### 4.4.4 关键设计：三道独立运行（不短路）

```
❌ 错误：短路
   if (!schemaOk) return; // 后面不跑了
   if (!policyOk) return;
   ...

✅ 正确：并联，结果合并
   const result = {
     schema: runSchemaCheck(plan),
     policy: runPolicyCheck(plan),
     scenario: runScenarioEval(plan),
   }
   // 一次性看到所有问题
```

**理由**：trace 要一次性暴露所有问题，让用户和 agent 都能看到完整的拒绝原因。

### 4.5 Approve（审批门）

#### 4.5.1 决策表

```
┌─────────────────┬──────────────┬─────────────────┐
│   riskLevel     │   检查结果    │     决策          │
├─────────────────┼──────────────┼─────────────────┤
│   read          │   全过        │   自动通过        │
│   read          │   有失败      │   拒绝            │
│   write-low     │   全过        │   自动通过        │
│   write-low     │   有失败      │   拒绝            │
│   write-high    │   全过        │   等待人工审批    │
│   write-high    │   有失败      │   拒绝            │
└─────────────────┴──────────────┴─────────────────┘
```

#### 4.5.2 人不是来"看 agent 做对没"

这是关于审批门最容易被误解的点：

```
❌ 错误理解
   人审批 = "再 review 一遍 agent 的工作"

✅ 正确理解
   人审批 = "承担那部分 agent 不该独自承担的责任"
```

差别在哪里：

```
┌────────────────────────────────────────────────────┐
│                                                    │
│   错误理解下：审批是冗余                             │
│   ↓                                                │
│   "如果 agent 都对了，那审批没用"                    │
│   "如果 agent 错了，那审批也救不回来"                │
│                                                    │
│   正确理解下：审批是责任分配                          │
│   ↓                                                │
│   "高风险动作的责任不应由 agent 单独承担"            │
│   "人需要在场，是因为出问题时该负责的是人"           │
│                                                    │
└────────────────────────────────────────────────────┘
```

#### 4.5.3 审批的最小要求

| 要求 | 说明 |
|---|---|
| **阻塞执行** | 真的等到显式动作发生，不能"超时默认通过" |
| **留下工件** | 谁批了什么、什么时候、批准还是拒绝 |
| **拒绝必须有理由** | 拒绝不能只是按个 X，要写原因 |
| **不可静默升级** | low → high 必须显式触发，不能因配置变化静默触发 |

### 4.6 Execute（执行）

```
┌────────────────────────── 执行规则 ─────────────────────────┐
│                                                            │
│  1. 必须事务性                                              │
│     ├── 全部成功 OR 全部回滚                                │
│     └── 部分写入是反模式                                    │
│                                                            │
│  2. 必须留 audit                                           │
│     ├── 每条变更写一条 audit_log                           │
│     └── 包含 before / after JSON                          │
│                                                            │
│  3. 失败必须明确                                            │
│     ├── 不允许静默吞异常                                    │
│     └── 必须 emit 失败事件                                  │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

伪代码：

```typescript
async function execute(plan: Plan, ctx: RunContext): Promise<ExecuteResult> {
  return await db.transaction(async (tx) => {
    const results = []
    for (const step of plan.steps) {
      try {
        const r = await tx.run(step.sql)
        await tx.insert("audit_log", {
          run_id: ctx.runId,
          action: step.sql,
          before_json: r.before,
          after_json: r.after,
          at: now(),
        })
        results.push(r)
        ctx.trace.emit("execute.committed", { step })
      } catch (e) {
        ctx.trace.emit("execute.rolled_back", { step, error: e.message })
        throw e // 触发事务回滚
      }
    }
    return { results }
  })
}
```

### 4.7 Trace（轨迹）

#### 4.7.1 三个角色

```
Trace 同时是三种东西：

  ① 调试工具
     工程师 review 异常运行时回放决策过程

  ② 审计工件
     合规、安全、问题归因的依据

  ③ 教学材料
     新人理解系统时的具体可触摸样本
```

#### 4.7.2 事件 kind 清单（典型）

```
intent.received
intent.normalized
plan.requested
plan.generated
plan.invalid_structure       ← LLM 输出不合法时
check.schema.passed | failed
check.policy.passed | failed
check.scenario.passed | failed
approval.required
approval.auto_granted
approval.user_approved
approval.user_rejected
execute.started
execute.committed
execute.rolled_back
finalize.<status>
```

#### 4.7.3 工件形态

```
runs/
├── 2026-04-15T10-32-44-r3k9/
│   ├── intent.json        ← 结构化意图
│   ├── plan.json          ← 结构化计划
│   ├── evaluation.json    ← 三道检查的合并结果
│   ├── report.md          ← 人类可读报告（合成的）
│   ├── trace.jsonl        ← 完整事件流
│   └── status             ← 单行状态
│
├── 2026-04-15T11-05-12-x7m2/
│   └── ...
```

**关键**：`runs/` 是 **append-only**。一次运行一旦 finalize，工件不再修改。

## 五、控制平面：四类工件

把"控制平面"展开看，所有工件落到四类。

### 5.1 Contracts（契约）

#### 5.1.1 形态

```typescript
// contracts/intent.schema.ts
import { z } from "zod"

export const IntentSpec = z.object({
  rawText: z.string(),
  goal: z.enum(["query", "aggregate", "mutate", "export"]),
  scope: z.object({
    tables: z.array(z.string()),
    timeWindow: z.object({
      from: z.string(),
      to: z.string(),
    }).optional(),
  }),
  assumptions: z.array(z.string()),
  riskLevel: z.enum(["read", "write-low", "write-high"]),
  successCriteria: z.array(z.string()),
})

export type IntentSpec = z.infer<typeof IntentSpec>
```

#### 5.1.2 一段代码同时是

```
┌──────────────────────────────────────────────┐
│                                              │
│   Zod Schema 同时承担三个角色                  │
│                                              │
│   ① 编译期类型                                │
│      type IntentSpec = z.infer<...>          │
│                                              │
│   ② 运行时校验                                │
│      IntentSpec.parse(unknownJson)           │
│                                              │
│   ③ 工件本身                                  │
│      文件可以被 commit、review、diff          │
│                                              │
└──────────────────────────────────────────────┘
```

这正是 TypeScript + Zod / Python + Pydantic 比裸 JSON Schema 更适合 harness 的原因。

### 5.2 Policies（规则）

#### 5.2.1 形态：声明式 yaml

```yaml
# policies/pii-fields.yaml
id: pii-fields
description: 禁止在 SELECT 中暴露 PII 列
applies_to:
  stages: [plan]
match:
  type: column-reference
  columns:
    - customers.email
    - customers.phone
    - customers.ssn
on_match:
  decision: reject
  message: "字段 {column} 是 PII，不允许暴露"
  suggestion: "改用 customers.id 或聚合后字段"
```

#### 5.2.2 关键边界：matcher 集合是封闭的

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│   yaml 不能变成 DSL                                  │
│                                                     │
│   ✅ 允许：声明已注册的 matcher                       │
│      type: column-reference                         │
│      type: table-without-where                      │
│      type: statement-kind                           │
│      type: row-budget                               │
│                                                     │
│   ❌ 禁止：在 yaml 里写新的逻辑                       │
│      condition: "x.foo > 100 && y.bar == 'baz'"    │
│      ↑ 这等于在 yaml 里写代码                        │
│                                                     │
│   规则：扩展能力先在解释器（policyCheck.ts）中        │
│         注册新 matcher，然后才能在 yaml 中使用        │
│                                                     │
└─────────────────────────────────────────────────────┘
```

这条边界保证 **yaml 永远是数据，不是 mini DSL**。

### 5.3 Scenarios（场景）

#### 5.3.1 与 Policy 的差异

```
Policy 关心规则           Scenario 关心状态
─────────────────         ─────────────────
不需要看真实数据           需要看真实数据 / 估算
                          
"PII 字段不允许"           "估算返回 10000 行"
"写操作要审批"             "跨表 join 深度 > 5"
                          
跑得快                     跑得慢（需要 EXPLAIN）
```

#### 5.3.2 形态

```yaml
# scenarios/row-budget.yaml
id: row-budget
description: 单次查询估算行数上限
type: explain-row-estimate
threshold:
  read: 10000
  write: 1000
on_exceed:
  decision: reject
  message: "估算返回 {rows} 行，超过 {threshold} 行上限"
  suggestion: "增加 LIMIT 或更精确的 WHERE 条件"
```

### 5.4 Prompts（模板）

#### 5.4.1 为什么 prompt 也是工件

```
┌──────────────────────────────────────────────┐
│                                              │
│   Prompt 不是代码常量字符串                    │
│                                              │
│   ❌ 错误：藏在 .ts 文件里                     │
│   const PROMPT = `You are a SQL planner...   │
│                   schema is: ${schema}...`   │
│                                              │
│   ✅ 正确：作为工件文件                        │
│   prompts/planner.tmpl                       │
│   You are a SQL planner.                     │
│   Schema: {{schema}}                         │
│   ...                                        │
│                                              │
│   理由：                                      │
│   - prompt 演化历史就是模型行为演化历史         │
│   - prompt 应当被 review、被 diff             │
│   - prompt 本质是"agent 的指令"，是规则的延伸   │
│                                              │
└──────────────────────────────────────────────┘
```

### 5.5 Runs（运行工件）

参见 §4.7。每次运行都产出一份可被 git 追踪的工件目录。

## 六、反馈回路的三种典型形态

理念 C 里说"工程师在构建反馈回路"。具体是哪些回路？

### 6.1 形态 1：检查 → 修复 → 重试

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│        检查 → 修复 → 重试回路                              │
│                                                          │
│   agent 生成 plan                                        │
│         │                                                │
│         ▼                                                │
│   policy 拦下                                            │
│         │                                                │
│         ▼                                                │
│   ┌──────────────────────┐                               │
│   │ 把"为什么被拦下"转写为  │                               │
│   │ 结构化反馈            │                               │
│   │                      │                               │
│   │ {                    │                               │
│   │   ruleId: "...",     │                               │
│   │   reason: "...",     │                               │
│   │   suggestion: "..."  │                               │
│   │ }                    │                               │
│   └──────────┬───────────┘                               │
│              │                                           │
│              ▼                                           │
│   作为新输入给 agent                                       │
│              │                                           │
│              ▼                                           │
│   agent 重写 plan                                         │
│              │                                           │
│              ▼                                           │
│   再次进入 check                                          │
│                                                          │
│   ────────────────────────────                           │
│   关键：反馈不是日志，是结构化输入                          │
│   ────────────────────────────                           │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**关键约束**：必须有重试上限（典型 2-3 次），否则陷入死循环。

### 6.2 形态 2：人工干预 → 学习

```
人审批 / 拒绝 → 工件留痕 → 喂回 prompt 上下文 / 转写新 policy

                                  ┌─────────────────┐
                                  │ 人拒绝："这个范围 │
                                  │ 太宽，不该批"     │
                                  └────────┬────────┘
                                           │
                              ┌────────────┴────────────┐
                              ▼                         ▼
                    ┌──────────────────┐   ┌──────────────────┐
                    │ 短期：把拒绝原因   │   │ 长期：把这条经验  │
                    │ 加入下次 plan 的   │   │ 转写为新 policy  │
                    │ prompt 上下文     │   │                  │
                    └──────────────────┘   └──────────────────┘
```

### 6.3 形态 3：场景演化 → 规则演化

```
真实运行被 trace 记录 → 工程师 review → 发现"该被拦下" → 转写规则

┌────────────────────────────────────────────────────┐
│                                                    │
│   runs/2026-03-12-x7k9/    ← 一次有问题的运行       │
│         │                                          │
│         │ 工程师 review                             │
│         ▼                                          │
│   "这次 agent 干了 X，下次同类情况应该被拦下"        │
│         │                                          │
│         │ 转写                                     │
│         ▼                                          │
│   policies/avoid-x.yaml    ← 新加一条规则           │
│         │                                          │
│         │ 部署后                                    │
│         ▼                                          │
│   下次同类情况 → 自动拦下                            │
│                                                    │
│   ───────────────────────────────                  │
│   工程师写的不是代码，是规则                         │
│   ───────────────────────────────                  │
│                                                    │
└────────────────────────────────────────────────────┘
```

### 6.4 三种回路的对比

| 回路 | 反馈给谁 | 时间尺度 | 工件 |
|---|---|---|---|
| 检查→修复→重试 | agent 自己 | 单次运行内 | trace 中的反馈事件 |
| 人工干预→学习 | 下一次 plan | 短期 | trace + 拒绝理由 |
| 场景演化→规则演化 | 整个系统 | 长期 | 新 policy 文件 |

## 七、与相邻概念的边界辨析

Harness Engineering 经常被误认为是已有概念的换名。逐个区分清楚。

### 7.1 vs Prompt Engineering

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│   Prompt Engineering                                 │
│   ↓                                                  │
│   关心：如何让模型输出正确                             │
│   类比："训练良马"                                    │
│                                                      │
│   Harness Engineering                                │
│   ↓                                                  │
│   关心：当模型输出不正确时，系统如何处理                │
│   类比："修路 + 配缰绳"                               │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**关系**：互补，不是替代。Prompt Engineering 优化 agent 内部，Harness 优化 agent 外部。

### 7.2 vs Agent Framework

```
LangChain / AutoGen / CrewAI ──── 实现工具
                                  解决"如何组织多个 agent 协作"

Harness Engineering ──────────── 工程范式
                                  解决"无论 agent 内部怎么组织，对外接口都必须可信"
```

**关系**：你可以用任何 framework，也可以不用，**Harness 主张是独立于 framework 的**。

### 7.3 vs RAG / Tool Use

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│   RAG ─────── 让 agent 知道更多                       │
│                                                      │
│   Tool Use ── 让 agent 能做更多                       │
│                                                      │
│   Harness ─── 让 agent 多做之后还是可信                │
│                                                      │
└──────────────────────────────────────────────────────┘
```

### 7.4 vs Guardrails

```
Guardrails ──── 内容层面的过滤（有害输出、PII、敏感词）
               范围窄、目的单一

Harness ──────  系统层面的工程范式
               包含 Schema / Policy / Scenario / Approval / Trace
               Guardrails 是 Harness 的一个子集
```

### 7.5 vs MLOps

```
MLOps ─────── 关心模型如何被训练、部署、监控
              生命周期：data → train → eval → deploy → monitor

Harness ───── 关心模型部署后，系统如何让它在生产中可靠运行
              生命周期：intent → plan → check → approve → execute → trace
```

### 7.6 边界总览

| 概念 | 关注 | 与 Harness 的关系 |
|---|---|---|
| Prompt Engineering | agent 内部 | 互补 |
| Agent Framework | 多 agent 协作 | 独立 |
| RAG | 给 agent 信息 | 互补 |
| Tool Use | 给 agent 能力 | 互补 |
| Guardrails | 内容过滤 | Harness 的子集 |
| MLOps | 模型生命周期 | 互补 |
| **Harness** | **agent 与世界的接口** | **本身** |

## 八、典型应用场景

Harness Engineering 不是绑死在某一类业务上的范式。下面四个场景演示它的可适配性。

### 8.1 场景一：SQL 查询助手

```
用户："上个月销售前 5 的产品"

┌──────────────────────────────────────────────────────┐
│  Intent  │ goal=aggregate, riskLevel=read            │
├──────────┼───────────────────────────────────────────┤
│  Plan    │ SELECT product_id, SUM(amount)            │
│          │ FROM orders WHERE date BETWEEN ... GROUP  │
├──────────┼───────────────────────────────────────────┤
│  Check   │ Schema: ✓ 字段存在                          │
│          │ Policy: ✓ 不涉及 PII / 有 WHERE             │
│          │ Scenario: ✓ 估算 < 10k 行                   │
├──────────┼───────────────────────────────────────────┤
│  Approve │ read → 自动通过                             │
├──────────┼───────────────────────────────────────────┤
│  Execute │ 执行查询，返回结果                           │
└──────────────────────────────────────────────────────┘

典型规则：
- PII 字段不允许出现在 SELECT
- orders 表查询必须带时间范围
- 写操作必须走审批
- 单次查询行数 ≤ 10k
```

### 8.2 场景二：代码审阅助手

```
用户：提交 PR #123 等待审阅

┌──────────────────────────────────────────────────────┐

│          │ ]                                          │
├──────────┼───────────────────────────────────────────┤
│  Check   │ Schema: ✓ 评论是结构化的                     │
│          │ Policy: ✓ 必须引用具体行号                   │
│          │ Policy: ✓ 决策必须给出具体理由               │
│          │ Scenario: ✓ 测试覆盖率没下降                 │
├──────────┼───────────────────────────────────────────┤
│  Approve │ Request Changes → 自动；LGTM → 人工         │
├──────────┼───────────────────────────────────────────┤
```

## 九、落地中的常见反模式

### 9.1 反模式 1：把 harness 写成代码

```typescript
// ❌ 反模式
function check(plan: Plan): Result {
  if (plan.sql.includes("email")) return reject("PII")
  if (!plan.sql.includes("WHERE")) return reject("missing WHERE")
  if (plan.sql.startsWith("UPDATE")) return needsApproval()
  return accept()
}
```

**判别**：删掉所有 yaml 文件后系统行为是否完全不变？是的话就是反模式。

### 9.2 反模式 2：审批门只是个 toast

```
❌ 错误
   弹个 alert("确认吗？")，按 OK 就过
   ↓
   这不是审批，是装饰

✅ 正确
   - 真正阻塞执行
   - 显式记录"谁批了什么、什么时候"
   - 拒绝必须有理由字段
   - 有独立命令边界（CLI 两阶段命令 / API 两个 endpoint）
```

### 9.3 反模式 3：trace 只是日志

```
❌ 错误
   logger.info("plan generated")
   logger.info("policy passed")
   logger.info("executed")
   ↓
   把日志重命名为 trace 没有意义

✅ 正确
   - 结构化（可被消费、可被 diff）
   - 完整（覆盖五阶段每一步）
   - 可阅读（合成的 markdown 报告能让陌生人看懂）
   - 持久化（可 git）
```

### 9.4 反模式 4：Demo Mode 走特殊路径

```
❌ 错误
   if (mode === "demo") {
     return { ok: true, result: hardcoded() }  // 跳过所有检查
   }

✅ 正确
   - Demo Mode 与 Live Mode 共用 schema/policy/scenario/approval/executor
   - 只在 Planner 那一步换实现
   - Demo 的故障注入也是真的走完整 pipeline
```

理由：如果 Demo 走的是不同路径，观众看到的只是 if-else，不是 harness 在工作。

### 9.5 反模式 5：把 yaml 写成 mini DSL

```yaml
❌ 反模式
   condition: "x.foo > 100 && y.bar == 'baz'"
   when: "user.role != 'admin' && time.hour > 18"
   ↑ 你在 yaml 里写代码

✅ 正确
   match:
     type: column-reference   ← 引用已注册的 matcher
     columns: [...]
```

**约束**：扩展能力先在解释器中注册新 matcher，再在 yaml 中使用。

### 9.6 反模式 6：用 harness 包装一切

```
❌ 错误
   每一个动作都强制走完整 5 阶段
   ↓
   "翻译这段文字" 也要 intent / plan / check / approve / execute

✅ 正确
   - 低风险只读 → Intent → Plan → Check → Execute → Trace
     （没有 Approve）
   - 高风险写入 → 完整 5 阶段
   - Harness 是按风险分级的，不是统一最严
```

### 9.7 反模式 7：契约只在代码里

```
❌ 错误
   契约只是 .ts 文件里的 interface
   ↓
   review 不到、diff 不到、没有"这是工件"的感觉

✅ 正确
   - 契约文件放在专门的目录（contracts/ 或 schemas/）
   - 用工具同时生成 JSON Schema 和 TS Type
   - 契约的演变史 = git log on contracts/*
```

### 9.8 反模式总览

| 反模式 | 判别信号 | 修正方向 |
|---|---|---|
| Harness 写成代码 | 删掉 yaml 行为不变 | 规则外化到 yaml |
| 审批是 toast | 不阻塞、无理由记录 | 两阶段 + 强制理由 |
| Trace 只是日志 | 字符串、非结构化 | 结构化事件 + JSONL |
| Demo 走特殊路径 | demo 跳过检查 | 共用下游 pipeline |
| yaml 变 DSL | yaml 里有表达式 | matcher 注册表封闭 |
| Harness 包一切 | 简单读也走 5 阶段 | 按风险分级 |
| 契约藏在代码 | 契约只是 interface | 专门目录 + 同步生成 |

## 十、最佳实践

### 10.1 设计阶段的最佳实践

```
1. 先画出五阶段流程图
   ─────────────────
   在写第一行代码之前，画出 Intent → Plan → Check → Approve → Execute → Trace
   每个阶段的输入输出是什么？

2. 先定契约，再写实现
   ─────────────────
   IntentSpec / Plan / EvaluationResult 必须先定义
   契约定下来之后，pipeline 各阶段就是"按契约串"

3. 控制平面与业务平面物理分离
   ─────────────────────────
   harness/ 与 src/db/ 互不感知
   业务写入只能由 executor 触碰

4. 规则用最小权限
   ──────────────
   policy 默认 reject
   显式列出"什么允许"而不是"什么禁止"
```

### 10.2 实现阶段的最佳实践

```
1. 双模式从一开始就考虑
   ─────────────────────
   Demo Mode 与 Live Mode 共用下游 pipeline
   Planner 是唯一可替换的部分

2. 每个 stage 都 emit trace
   ────────────────────────
   trace 不是事后加的"日志"
   而是 stage 的强制副作用

3. Schema / Policy / Scenario 三道独立运行
   ────────────────────────────────────────
   不要短路，让 trace 一次性看到所有问题

4. 审批走独立命令边界
   ────────────────
   不要在同一个进程里阻塞等待
   两阶段命令 / 两个 endpoint 让审批是独立动作
```

### 10.3 演进阶段的最佳实践

```
1. 新规则先加 matcher 再加 yaml
   ──────────────────────────
   不要让 yaml 表达力越界
   matcher 注册表是封闭的

2. 失败的运行要被研究
   ──────────────────
   runs/ 不只是历史，是规则演化的素材
   定期 review 失败 / 拒绝 / 审批的运行

3. 规则版本化
   ──────────
   policies/ 进 git，每条规则的演化史可见
   重大规则变更走 PR review

4. trace 要可被检索
   ────────────────
   长期看要把 runs/ 接到一个查询界面
   按 ruleId / status / 时间窗口检索
```

### 10.4 团队协作的最佳实践

```
┌──────────────────────────────────────────────────┐
│                                                  │
│   传统团队角色             Harness 团队角色        │
│   ───────────             ──────────────         │
│                                                  │
│   后端工程师               契约 / 规则工程师        │
│     ↓                       ↓                    │
│   写业务代码                 写 schema 和 policy   │
│                                                  │
│   QA / 测试                 场景设计师             │
│     ↓                       ↓                    │
│   写测试用例                 设计 scenario 检查    │
│                                                  │
│   产品 / 业务               审批者                 │
│     ↓                       ↓                    │
│   定义需求                   定义高风险动作        │
│                                                  │
└──────────────────────────────────────────────────┘
```

## 十一、参考实现：harness-demo

> 项目地址：**[github.com/Perlou/harness-demo](https://github.com/Perlou/harness-demo)**

为了让上面所有抽象概念都落到具体可触摸的代码上，我们配套了一份完整的
开源参考实现 —— **harness-demo**。它是一个 SQL 查询助手 CLI：用户输入
自然语言（"上个月销售前 5 的产品"），系统按本范式生成 SQL 并必须经过完整
五阶段 pipeline 才能真正动数据库。

### 11.1 项目概览

| 维度 | 数据 |
|---|---|
| 主语言 | TypeScript（strict + NodeNext ESM） |
| 业务面 | 6 表电商 SQLite 库（Mulberry32 PRNG 确定性 seed） |
| 控制平面 | 4 份 Zod 契约 + 3 条 yaml policy + 1 个 scenario + 2 份 prompt 模板 |
| 测试 | 98 个用例 / 整体覆盖率 93.89%（pipeline 91.26%） |
| 模式 | Demo（关键词分类）+ Live（OpenAI Chat Completions）**共用下游** |
| 发布 | npm scoped 包 + Docker GHCR 多架构（amd64 + arm64）+ tag-driven CI/CD |

### 11.2 控制平面与业务平面的物理分离

```
harness-demo/
├─ harness/                  控制平面（数据 / 工件，无业务逻辑）
│  ├─ contracts/             Zod schemas（IntentSpec / Plan / EvaluationResult）
│  ├─ policies/              声明式 yaml 规则（matcher 注册表封闭）
│  ├─ scenarios/             状态相关检查（行数预算等）
│  └─ prompts/               Live Mode 用的 prompt 模板
├─ src/
│  ├─ pipeline/              5 阶段引擎（薄壳，不持有规则）
│  ├─ planners/              demo / live 两个 Planner 实现
│  ├─ db/                    业务平面（仅 executor 触碰写）
│  └─ trace/                 事件总线 + 工件写入 + 报告渲染
└─ runs/<id>/                每次运行的工件目录（gitignored）
   ├─ intent.json
   ├─ plan.json
   ├─ evaluation.json
   ├─ report.md              人类可读报告（6 大节）
   ├─ trace.jsonl            完整事件流
   └─ status                 单行状态机
```

**教学红线**：删任意一份 `harness/*.yaml`，系统行为应当发生**可观察变化**。
否则说明规则没有真正被外化。

### 11.3 四个出厂剧本

每个剧本对应一份可被反复演示的 trace 工件，覆盖 harness 各阶段的拦截路径：

| 剧本 | 输入 | harness 拦截点 | 终态 |
|---|---|---|---|
| **A · happy path** | 上个月销售前 5 的产品 | 全过 → 自动放行 | `committed` |
| **B · PII 拦截** | 导出所有客户的邮箱和手机号 | Policy: `pii-fields` | `rejected_by_policy` |
| **C · 缺时间过滤** | orders 表里有多少行 | Policy: `require-time-bounds` | `rejected_by_policy` |
| **D · 写操作审批** | 把已发货 90 天的订单标记为已完成 | `destructive-needs-approval` 升级 | `pending-approval` |

剧本 D 还演示了**两阶段审批**的完整路径：`harness ask` 后产物落到
`pending-approval` 状态，需要人手动 `harness approve <run-id>` 或
`harness reject <run-id> --reason "..."` 才会触发真正的写入或拒绝。

### 11.5 同一下游证明

仓库里专门有一组测试演示**同一份下游 pipeline 同时约束规则系统和真实模型**：

```ts
// 让"假 LLM"故意输出含 PII 的 SQL
setLivePlannerClientForTests(fakeClient(JSON.stringify({
  steps: [{ kind: "sql", mode: "read",
```

```
│                三种反馈回路                                          │
│                ────────────                                        │
│                检查→修复→重试                                        │
│                人工干预→学习                                         │
│                场景演化→规则演化                                     │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### 12.2 推荐学习路径

```
Week 1: 理念建立
├── 阅读 OpenAI 关于 Harness Engineering 的原始论述
├── 理解三条核心理念（工件 / 约束 / 脚手架）
├── 区分 Harness 与 Prompt Engineering / Agent Framework
└── 在熟悉的业务场景上画一遍五阶段流程

Week 2: 契约与规则
├── 学习 Zod / Pydantic 等契约工具
├── 写第一份 IntentSpec / Plan schema
├── 把日常工作中的"隐式规则"列出来
└── 试着把其中 3 条转写为 yaml 形态的 policy

Week 3: 落地一个最小 demo
├── 选一个有边界的业务（SQL 助手 / 部署助手 / 审阅助手）
├── 实现 Intent → Plan → Check → Approve → Execute → Trace
├── 实现两阶段审批命令
└── 让每次运行产生 runs/<id>/ 工件

Week 4: Live Mode + 反馈回路
├── 接入真实 LLM
├── 让下游 pipeline 不变
├── 实现"检查→修复→重试"
└── 设计 trace 可视化

Week 5+: 团队应用
├── 把契约 / 规则纳入 PR review 流程
├── 把规则演化纳入团队迭代
├── 定期 review 失败运行 → 沉淀新规则
└── 在团队层面建立 harness 工程师角色
```

### 12.3 自我检查清单

落地一个 harness 系统时，对照以下清单检查：

```
□ 删掉所有 yaml 后，系统行为是否会变化？（应该变化）
□ 控制平面（harness/）与业务平面（db/）是否物理分离？
□ 每次运行是否产出可被 git 追踪的工件？
□ 审批门是否真的阻塞，且留下"谁批了什么"的工件？
□ Demo Mode 与 Live Mode 是否共用下游 pipeline？
□ Trace 是否结构化、可被消费、可还原决策过程？
□ 五个阶段是否都有 emit 至少一个事件？
□ 失败的运行是否被保留，可被 review？
□ 规则演化是否走 PR / review 流程？
□ 是否有按风险分级（不是所有动作都强制 5 阶段）？
```

### 12.5 一段话作为结尾

> Harness Engineering 真正在说的事，是**软件工程的核心产出物正在变化**。
>
> 过去工程师交付的是代码。现在最有价值的交付物正在变成：**契约**（系统该接受什么）、**规则**（什么情况下做什么决定）、**环境**（agent 能看到什么、能动什么）、**反馈回路**（系统如何从每次运行学到经验）。
>
> 代码仍然要写，但写代码这件事正在被 agent 接管。**为 agent 设计能跑得稳的世界 —— 这件事是当下工程师真正的杠杆所在。**

---

> 💡 提示：Harness Engineering 仍是非常新的范式，建议结合自己的真实工作场景反复推敲。本文核心理念在变化时不大，落地形态会随工具链演进。
