## RAG 基础概念

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将**信息检索**与**大语言模型生成**结合的技术范式。

### 核心思想

```
用户问题 → 检索相关文档 → 将文档注入 Prompt → LLM 生成答案
```

### 解决的核心问题

| 问题 | 说明 |
|------|------|
| 知识截止 | LLM 训练数据有时效性限制 |
| 幻觉问题 | LLM 容易生成看似合理但错误的内容 |
| 私域知识 | 企业内部数据无法训练进模型 |
| 可溯源性 | 无法追踪答案来源 |

### RAG 演进路径

```
Naive RAG → Advanced RAG → Modular RAG
                ↓
     Self-RAG / CRAG / HyDE
                ↓
     Graph RAG / Agentic RAG
```

## Naive RAG（朴素RAG）

### 概述

最基础的 RAG 实现，遵循 **索引 → 检索 → 生成** 的标准三段式流程。

### 架构流程

```
┌─────────────────────────────────────────────────────┐
│                    离线索引阶段                        │
│                                                      │
│  原始文档 → 文本清洗 → 分块(Chunk) → 向量化 → 向量数据库 │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│                    在线检索阶段                        │
│                                                      │
│  用户问题 → 向量化 → 相似度检索 → Top-K 文档           │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│                    生成阶段                           │
│                                                      │
│  [问题 + Top-K文档] → Prompt → LLM → 最终答案         │
└─────────────────────────────────────────────────────┘
```

### 核心步骤详解

#### 1. 文档分块（Chunking）

```python
# 固定大小分块示例
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=64,  # 重叠部分保持上下文连续性
    separators=["\n\n", "\n", "。", ".", " "]
)
chunks = splitter.split_documents(documents)
```

**常见分块策略：**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 固定大小 | 按字符数切割 | 通用场景 |
| 句子分割 | 按句号/换行切割 | 新闻、文章 |
| 段落分割 | 按段落结构切割 | 结构化文本 |
| 递归分割 | 多级分隔符递归切割 | 混合文本 |

#### 2. 向量化（Embedding）

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer('BAAI/bge-large-zh-v1.5')
embeddings = model.encode(chunks, normalize_embeddings=True)
```

#### 3. 相似度检索

```python
# 余弦相似度检索
import faiss
import numpy as np

index = faiss.IndexFlatIP(embedding_dim)  # 内积 = 归一化后的余弦相似度
index.add(embeddings)

query_embedding = model.encode([query])
scores, indices = index.search(query_embedding, k=5)  # Top-5
```

#### 4. Prompt 构建

```
你是一个专业的问答助手，请根据以下上下文回答用户问题。

【上下文】
{retrieved_docs}

【用户问题】
{query}

【要求】
- 只使用上下文中的信息进行回答
- 如果上下文中没有相关信息，请如实说明
- 回答要简洁准确
```

### 存在的问题

```
❌ 检索质量问题
   - 语义鸿沟：查询与文档表达方式不同导致检索失败
   - 固定 Top-K：无论相关性如何都返回固定数量

❌ 生成质量问题  
   - 上下文过长导致"迷失在中间"现象
   - 检索到不相关文档干扰生成
   - 答案无法跨多个文档推理

❌ 工程问题
   - 分块粒度难以平衡（太细丢失上下文，太粗引入噪声）
   - 无法处理表格、图片等非文本内容
```

## Advanced RAG（高级RAG）

### 概述

针对 Naive RAG 的缺陷进行系统性优化，在**预检索、检索、后检索**三个阶段分别增强。

### 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│                        预检索优化                              │
│  查询改写 | 查询扩展 | HyDE | 查询路由                          │
└──────────────────────────────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────┐
│                        检索优化                               │
│  混合检索 | 多路召回 | 父文档检索 | 句子窗口检索                  │
└──────────────────────────────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────┐
│                        后检索优化                              │
│  重排序(Reranker) | 上下文压缩 | 文档过滤                       │
└──────────────────────────────────────────────────────────────┘
```

### 预检索优化

#### 查询改写（Query Rewriting）

```python
# 使用 LLM 改写查询，使其更适合检索
rewrite_prompt = """
请将以下用户问题改写为更适合文档检索的搜索查询，
保留核心语义，使用更规范的表达方式。

原始问题：{query}
改写后的搜索查询：
"""

rewritten_query = llm.invoke(rewrite_prompt.format(query=user_query))
```

#### 查询扩展（Query Expansion）

```
原始查询："如何提高睡眠质量"
                ↓
扩展查询：
  - "改善睡眠的方法"
  - "失眠的解决办法"  
  - "睡眠障碍调理"
  - "提高睡眠深度技巧"
```

**Multi-Query 策略：**

```python
from langchain.retrievers.multi_query import MultiQueryRetriever

retriever = MultiQueryRetriever.from_llm(
    retriever=vectorstore.as_retriever(),
    llm=llm
)
# 自动生成多个查询变体，取并集检索结果
docs = retriever.get_relevant_documents(query)
```

#### Step-Back Prompting

```
原始问题："为什么 Python 的 GIL 会影响多线程性能？"
         ↓ Step-Back
抽象问题："什么是 GIL？Python 的并发模型是什么？"
         ↓ 先检索背景知识，再回答具体问题
```

### 检索优化

#### 混合检索（Hybrid Search）

```
稀疏检索（BM25）   ──┐
                      ├→ RRF 融合 → 最终排序结果
稠密检索（向量）   ──┘

RRF 融合公式：
Score(d) = Σ 1/(k + rank_i(d))
其中 k=60，rank_i 为第 i 个检索器中文档 d 的排名
```

```python
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever

bm25_retriever = BM25Retriever.from_documents(docs, k=5)
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.4, 0.6]  # 稀疏:稠密 = 4:6
)
```

#### 父文档检索（Parent Document Retriever）

```
索引阶段：
原始文档 → 切割为小块(子文档) → 向量化索引
         → 同时存储父文档(大块)

检索阶段：
查询 → 检索小块(精确匹配) → 返回对应父文档(完整上下文)

优势：检索精度 + 上下文完整性 兼得
```

```
┌─────────────────────────────────────────────┐
│                父文档（512 tokens）           │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐   │
│  │子块1  │  │子块2  │  │子块3  │  │子块4  │   │
│  │128t  │  │128t  │  │128t  │  │128t  │   │
│  └──────┘  └──────┘  └──────┘  └──────┘   │
└─────────────────────────────────────────────┘
    ↑ 向量检索命中子块2，返回整个父文档
```

#### 句子窗口检索（Sentence Window Retrieval）

```
索引：对每个句子单独向量化
检索：找到最匹配的句子后，扩展返回其上下文窗口

例：命中第5句 → 返回 [第3句, 第4句, 第5句, 第6句, 第7句]
```

### 后检索优化

#### 重排序（Reranking）

```
初步检索（召回阶段）：向量相似度 → Top-20 候选文档
                              ↓
精排阶段（Rerank）：Cross-Encoder → Top-5 精准结果
                              ↓
                         注入 Prompt
```

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder('BAAI/bge-reranker-large')

# 计算每个文档与查询的相关性分数
pairs = [[query, doc.page_content] for doc in retrieved_docs]
scores = reranker.predict(pairs)

# 按分数重新排序
ranked_docs = sorted(
    zip(retrieved_docs, scores), 
    key=lambda x: x[1], 
    reverse=True
)
top_docs = [doc for doc, score in ranked_docs[:5]]
```

**双塔 vs 交叉编码器对比：**

| 特性 | 双塔模型（Bi-Encoder） | 交叉编码器（Cross-Encoder） |
|------|----------------------|--------------------------|
| 原理 | 独立编码查询和文档 | 联合编码查询-文档对 |
| 速度 | 快（可预计算） | 慢（实时计算） |
| 精度 | 较低 | 高 |
| 用途 | 初步召回 | 精排重排序 |

#### 上下文压缩（Context Compression）

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor

compressor = LLMChainExtractor.from_llm(llm)

compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=retriever
)
# 自动提取文档中与问题最相关的片段
```

## Modular RAG（模块化RAG）

### 概述

将 RAG 系统拆解为**独立可组合的模块**，通过灵活编排实现定制化 RAG 流程。

### 核心模块体系

```
┌─────────────────────────────────────────────────────────────┐
│                      Modular RAG 模块图                      │
├──────────┬──────────┬──────────┬──────────┬────────────────┤
│  索引模块  │  检索模块  │  预测模块  │  编排模块  │   记忆模块      │
├──────────┼──────────┼──────────┼──────────┼────────────────┤
│ 分块策略  │ 向量检索  │ LLM生成  │ 路由选择  │ 对话历史        │
│ 多模态索引│ BM25检索  │ 提示工程  │ 调度控制  │ 知识缓存        │
│ 知识图谱  │ 混合检索  │ 输出解析  │ 迭代控制  │ 全局记忆        │
│ 元数据过滤│ 重排序   │ 验证校验  │ 分支决策  │                │
└──────────┴──────────┴──────────┴──────────┴────────────────┘
```

### 查询路由（Query Routing）

```python
# 根据问题类型路由到不同数据源
routing_prompt = """
分析用户问题，判断应该查询哪个数据源：
- "product_db"：产品相关问题
- "hr_wiki"：人力资源政策问题
- "tech_docs"：技术文档问题
- "general"：通用问答

用户问题：{query}
输出（只输出数据源名称）：
"""

def route_query(query):
    route = llm.invoke(routing_prompt.format(query=query))
    return retrievers[route.strip()]
```

### 自适应检索流程

```
用户问题
    ↓
┌─────────────┐
│  问题分析器  │ → 判断问题类型、复杂度
└─────────────┘
    ↓
┌──────────┬──────────┬──────────┐
│ 简单问题  │ 复杂问题  │ 多跳问题  │
│ 单次检索  │ 分解检索  │ 链式检索  │
└──────────┴──────────┴──────────┘
    ↓
┌─────────────┐
│  结果合并   │
└─────────────┘
    ↓
  最终答案
```

### 典型编排模式

#### 顺序管道（Sequential Pipeline）

```
Query → 改写 → 检索 → 重排 → 压缩 → 生成
```

#### 分支管道（Branching Pipeline）

```
              ┌→ 向量检索 ─┐
Query → 路由 ─┤             ├→ 合并 → 重排 → 生成
              └→ BM25检索 ─┘
```

#### 迭代管道（Iterative Pipeline）

```
Query → 检索 → 生成 → 评估 → [不满足] → 再检索 → ...
                           → [满足]  → 输出
```

## Graph RAG

### 概述

微软提出的方案，将文档构建为**知识图谱**，利用图结构进行检索，特别擅长处理**跨文档推理**和**全局性问题**。

### 核心思想

```
传统 RAG：文档 → 向量 → 相似度检索（局部）
Graph RAG：文档 → 知识图谱 → 图遍历检索（全局 + 局部）
```

### 构建流程

```
┌─────────────────────────────────────────────────────────┐
│                    离线构建阶段                            │
│                                                         │
│  文档                                                    │
│   ↓                                                     │
│  实体抽取（LLM）→ [人物、地点、概念、事件...]               │
│   ↓                                                     │
│  关系抽取（LLM）→ [实体A --关系--> 实体B]                  │
│   ↓                                                     │
│  社区检测（Leiden算法）→ 实体聚类分组                        │
│   ↓                                                     │
│  社区摘要（LLM）→ 每个社区生成摘要报告                       │
│   ↓                                                     │
│  知识图谱 + 社区摘要 存储                                  │
└─────────────────────────────────────────────────────────┘
```

### 知识图谱结构

```
        ┌─────────┐
        │  苹果公司 │
        └────┬────┘
             │ 创立
    ┌────────┴────────┐
    │                 │
┌───┴───┐         ┌───┴───┐
│乔布斯  │         │沃兹尼亚克│
└───┬───┘         └───────┘
    │ 发布
┌───┴──────┐
│  iPhone  │──── 基于 ────→ ┌──────┐
└──────────┘               │ iOS  │
                           └──────┘
```

### 双模式检索

#### Local Search（局部搜索）

适用于：**具体实体/关系**相关的问题

```
查询 → 实体识别 → 图遍历（1-2跳邻居）→ 相关文本+关系 → 生成
```

#### Global Search（全局搜索）

适用于：**宏观/汇总**类问题（如"文档主要讲了什么？"）

```
查询 → 筛选相关社区摘要 → Map阶段（各社区并行生成局部答案）
     → Reduce阶段（汇总所有局部答案）→ 最终答案
```

### Graph RAG vs 传统 RAG

| 维度 | 传统 RAG | Graph RAG |
|------|---------|-----------|
| 知识组织 | 平铺文档块 | 图结构知识 |
| 关系推理 | 弱 | 强 |
| 全局问答 | 差 | 好 |
| 构建成本 | 低 | 高 |
| 实时更新 | 容易 | 复杂 |
| 适用场景 | 精确问答 | 分析/推理 |

### 实现示例

```python
from graphrag.index import run_pipeline_with_config
from graphrag.query.structured_search.local_search.search import LocalSearch
from graphrag.query.structured_search.global_search.search import GlobalSearch

# 本地搜索（具体问题）
local_search = LocalSearch(
    llm=llm,
    context_builder=local_context_builder,
    entity_text_embeddings=entity_embeddings,
    text_embedder=embedder
)
result = await local_search.asearch("张三和李四有什么关系？")

# 全局搜索（宏观问题）
global_search = GlobalSearch(
    llm=llm,
    context_builder=global_context_builder,
    max_data_tokens=12000
)
result = await global_search.asearch("这些文档的主要主题是什么？")
```

## Agentic RAG

### 概述

将 RAG 与 **AI Agent** 结合，LLM 作为决策核心，自主决定何时检索、检索什么、是否需要多次检索。

### 与传统 RAG 的核心区别

```
传统 RAG：固定流程（Query → Retrieve → Generate）
Agentic RAG：动态决策（LLM 自主规划多步骤检索和推理）
```

### 架构模式

#### 单 Agent 模式

```
用户问题
    ↓
┌─────────────────────────────────────────┐
│              ReAct Agent                │
│                                         │
│  Thought: 我需要先了解A，再查询B         │
│  Action: search("A的定义")              │
│  Observation: [检索结果]                │
│  Thought: 现在我需要查B与A的关系         │
│  Action: search("B与A的关系")           │
│  Observation: [检索结果]                │
│  Thought: 信息足够，可以回答了           │
│  Answer: 综合答案...                    │
└─────────────────────────────────────────┘
```

#### 多 Agent 模式

```
                 ┌──────────────┐
                 │  主控 Agent  │
                 │（任务规划器）  │
                 └──────┬───────┘
                        │ 分配子任务
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │检索Agent │  │计算Agent │  │验证Agent │
   │专注信息  │  │专注数学  │  │专注核实  │
   │检索      │  │推理      │  │答案      │
   └──────────┘  └──────────┘  └──────────┘
          └─────────────┬─────────────┘
                        ↓
                   汇总最终答案
```

### 工具集设计

```python
tools = [
    Tool(
        name="向量检索",
        description="从知识库检索语义相关内容，适合概念性问题",
        func=vector_search
    ),
    Tool(
        name="关键词搜索",
        description="精确关键词匹配，适合查找特定术语或名称",
        func=bm25_search
    ),
    Tool(
        name="SQL查询",
        description="从数据库查询结构化数据，适合统计类问题",
        func=sql_query
    ),
    Tool(
        name="网络搜索",
        description="搜索最新的互联网信息",
        func=web_search
    ),
    Tool(
        name="计算器",
        description="执行数学计算",
        func=calculator
    )
]
```

### ReAct 实现示例

```python
from langchain.agents import create_react_agent, AgentExecutor
from langchain import hub

prompt = hub.pull("hwchase17/react")

agent = create_react_agent(llm=llm, tools=tools, prompt=prompt)
agent_executor = AgentExecutor(
    agent=agent,
    tools=tools,
    verbose=True,
    max_iterations=10,
    handle_parsing_errors=True
)

result = agent_executor.invoke({
    "input": "2024年特斯拉的营收是多少？比2023年增长了多少？"
})
```

### Plan-and-Execute 模式

```
问题：分析苹果和微软在AI领域的战略布局差异

Step 1: 检索苹果AI战略相关文档
```

## Self-RAG

### 概述

Self-RAG（2023, Asai et al.）让 LLM **自我反思**，通过生成特殊的反思 Token 来决定是否检索、评估检索质量和生成质量。

### 反思 Token 体系

```
┌─────────────────────────────────────────────────────────┐
│                    反思 Token 类型                        │
├─────────────┬───────────────────────────────────────────┤
│ Retrieve    │ [Retrieve] / [No Retrieve]                 │
│             │ 判断是否需要检索                             │
├─────────────┼───────────────────────────────────────────┤
│ ISREL       │ [Relevant] / [Irrelevant]                  │
│             │ 判断检索文档是否相关                          │
├─────────────┼───────────────────────────────────────────┤
│ ISSUP       │ [Fully Supported] / [Partially Supported]  │
│             │ / [No Support]                             │
│             │ 判断生成内容是否有文档支撑                    │
├─────────────┼───────────────────────────────────────────┤
│ ISUSE       │ [Utility:1~5]                              │
│             │ 评估答案对用户的实用性（1-5分）               │
└─────────────┴───────────────────────────────────────────┘
```

### 工作流程

```
用户输入
    ↓
LLM 判断：是否需要检索？
    ↓
[No Retrieve]              [Retrieve]
    ↓                          ↓
直接生成答案              执行检索获取文档
                               ↓
                    对每个文档评估：[ISREL]
                               ↓
                    并行生成多个候选答案
                               ↓
                    评估每个答案：[ISSUP] + [ISUSE]
                               ↓
                    选择最高评分的答案输出
```

### 示例展示

```
问题：爱因斯坦获得诺贝尔奖是因为相对论吗？

LLM 输出：
[Retrieve] 我需要检索爱因斯坦获得诺贝尔奖的原因

检索文档：《1921年诺贝尔物理学奖》

[Relevant] 该文档与问题相关

候选答案生成：
"爱因斯坦获得1921年诺贝尔物理学奖是因为发现了光电效应定律。"

[Fully Supported] 答案完全由文档支撑
[Utility: 5] 答案完整回答了问题

最终答案：不是。爱因斯坦的诺贝尔奖是因为发现光电效应定律，
         而非相对论。
```

### Self-RAG vs 传统 RAG

| 特性 | 传统 RAG | Self-RAG |
|------|---------|---------|
| 是否总是检索 | 是 | 自适应 |
| 检索质量评估 | 无 | 有 |
| 生成质量评估 | 无 | 有 |
| 需要特殊训练 | 否 | 是（微调） |
| 计算成本 | 低 | 高 |

## Corrective RAG（CRAG）

### 概述

CRAG 引入**纠错机制**，对检索结果进行评估，当发现检索质量不佳时自动启动纠错流程（如网络搜索补充）。

### 核心流程

```
用户问题
    ↓
向量检索 → Top-K 文档
    ↓
轻量级评估器（Relevance Evaluator）
    ↓
┌─────────────────────────────────────────────┐
│  评估结果                                    │
├──────────┬──────────────┬───────────────────┤
│  CORRECT │  AMBIGUOUS   │    INCORRECT      │
│  高度相关 │   部分相关   │    完全不相关      │
├──────────┼──────────────┼───────────────────┤
│ 知识精炼  │ 知识精炼     │ 放弃检索结果      │
│ 直接使用  │  +           │  +               │
│          │ Web搜索补充  │ Web搜索替代       │
└──────────┴──────────────┴───────────────────┘
    ↓               ↓               ↓
              合并知识源
                  ↓
              生成最终答案
```

### 知识精炼（Knowledge Refinement）

```python
# 将检索文档分解为细粒度知识条目，过滤不相关部分
def knowledge_refinement(document, query):
    strips = split_into_sentences(document)
    
    relevant_strips = []
    for strip in strips:
        relevance = evaluator.score(query, strip)
        if relevance > threshold:
            relevant_strips.append(strip)
    
    return " ".join(relevant_strips)
```

### 评估器设计

```python
# 轻量级相关性评估器（通常用小模型）
class RelevanceEvaluator:
    def evaluate(self, query, document):
        """
        返回：
        - CORRECT: score > 0.8
        - AMBIGUOUS: 0.4 < score <= 0.8  
        - INCORRECT: score <= 0.4
        """
        score = self.model.predict(query, document)
        if score > 0.8:
            return "CORRECT"
        elif score > 0.4:
            return "AMBIGUOUS"
        else:
            return "INCORRECT"
```

## HyDE（假设文档嵌入）

### 概述

HyDE（Hypothetical Document Embeddings）让 LLM 先**假设性地生成**一个理想答案文档，然后用这个假设文档的向量去检索真实文档库。

### 核心思路

```
传统方式：查询向量 ──→ 相似度匹配 ──→ 文档
HyDE方式：查询 → LLM生成假设文档 → 假设文档向量 ──→ 相似度匹配 ──→ 真实文档
```

### 为什么有效？

```
问题空间（查询）     知识空间（文档）
       |                    |
"什么是黑洞？"   ←→   "黑洞是一种...的天体..."
       |                    |
  查询向量         文档向量
  (问题语义)       (答案语义)
  
存在语义鸿沟！

HyDE：
"什么是黑洞？" → LLM → "黑洞是引力极强的天体..." → 向量
                              ↓
                     与真实文档在同一语义空间
```

### 实现

```python
from langchain.chains import HypotheticalDocumentEmbedder
from langchain.chains import LLMChain

# 生成假设文档的 Prompt
hyde_prompt = """
请为以下问题写一段简短的、可能包含答案的文档段落（100字左右）：

问题：{question}
假设文档：
"""

hyde_chain = LLMChain(llm=llm, prompt=PromptTemplate.from_template(hyde_prompt))

def hyde_retrieve(query, vectorstore, k=5):
    # Step 1: 生成假设文档
    hypothetical_doc = hyde_chain.run(question=query)
    
    # Step 2: 对假设文档进行向量化
    hyp_embedding = embedder.embed_query(hypothetical_doc)
    
    # Step 3: 用假设文档向量检索真实文档
    real_docs = vectorstore.similarity_search_by_vector(hyp_embedding, k=k)
    
    return real_docs
```

### HyDE 效果示意

```
查询：       "量子计算机比传统计算机快多少？"

假设文档：   "量子计算机利用量子叠加和纠缠原理，
             在特定任务上可比传统计算机快数百万倍。
             例如Shor算法在因数分解上展示了指数级加速..."

检索结果：   ✅ 《量子计算加速原理》
             ✅ 《量子vs经典计算性能对比》
             ✅ 《Shor算法详解》
             
vs 直接检索：
             ❌ 《什么是量子计算机》（相关但不精准）
             ❌ 《计算机发展历史》（不相关）
```

### 综合对比表

| 方案 | 核心创新 | 优势 | 劣势 | 推荐场景 |
|------|---------|------|------|---------|
| **Naive RAG** | 基础三段式 | 简单易实现 | 效果有限 | 快速原型 |
| **Advanced RAG** | 多阶段优化 | 效果好，通用 | 链路复杂 | 生产环境首选 |
| **Modular RAG** | 模块化编排 | 灵活可定制 | 需要设计能力 | 复杂业务系统 |
| **Graph RAG** | 知识图谱 | 关系推理强 | 构建成本高 | 知识密集型分析 |
| **Agentic RAG** | 自主决策 | 处理复杂问题 | 延迟高、不稳定 | 多步骤复杂任务 |
| **Self-RAG** | 自我反思 | 高质量输出 | 需要微调模型 | 高精度要求场景 |
| **CRAG** | 纠错机制 | 鲁棒性强 | 依赖网络搜索 | 知识库不完整场景 |
| **HyDE** | 假设文档 | 提升召回率 | 可能引入幻觉 | 知识型问答增强 |

## 最佳实践建议

### 1. 分块策略选择

```
文档类型 → 推荐分块策略：
- 长文章/报告   → 递归分割 (512 tokens, overlap 64)
- 技术文档      → 父子文档检索
- 对话/QA数据   → 按问答对分割  
- 代码文件      → 按函数/类分割
- 结构化表格    → 行列语义化后分割
```

### 2. Embedding 模型选择原则

```
中文场景   → BAAI/bge 系列
英文场景   → OpenAI Ada / E5
多语言     → multilingual-e5-large
长文本     → nomic-embed-text (支持8192 tokens)
实时更新   → 优先用 API 服务避免本地部署
```

### 3. 性能优化

```python
async def parallel_retrieve(queries, retriever):
    tasks = [retriever.aget_relevant_documents(q) for q in queries]
    results = await asyncio.gather(*tasks)
    return results
```

### 4. 评估体系

```
RAG 评估维度：

检索质量：
├── Context Precision    # 检索内容的精准率
├── Context Recall       # 检索内容的召回率
└── Context Relevancy    # 检索内容的相关性

生成质量：
├── Faithfulness         # 答案是否忠实于上下文
├── Answer Relevancy     # 答案是否回答了问题
└── Answer Correctness   # 答案是否正确

工具推荐：RAGAS 框架
```

> **总结**：RAG 技术没有银弹，需要根据具体业务场景、数据特点、延迟要求和成本预算综合选择。建议从 **Advanced RAG** 起步，根据实际痛点逐步引入 **Graph RAG**（提升推理）、**CRAG**（提升鲁棒性）或 **Agentic RAG**（处理复杂任务）。
